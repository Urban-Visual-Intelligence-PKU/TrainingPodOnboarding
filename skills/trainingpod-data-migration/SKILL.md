# TrainingPod 申请、登录和数据迁移

## 申请 Pod

1. 先收集个人目录名、GitHub 用户名和出网方式（直连或代理），并确认是首次申请还是追加已有目录的 Pod。个人目录名以小写字母开头，长度 1–10 位，仅含小写字母和数字，避开 `root`、`ubuntu`、`shared`。提醒用户把本机 OpenSSH 公钥添加到该 GitHub 账号的 **Settings → SSH and GPG keys**，类型选 **Authentication Key**，私钥保存在本机。
2. 收齐后输出以下三行供用户直接复制给管理员。替换示例值，出网方式只填所选的一项。

   ```text
   个人目录名：huyuan
   GitHub 用户名：Lavender105
   出网方式：直连
   ```

   追加时沿用已有目录名，请用户另发一句「请为这个已有个人目录追加一个 Pod」，无需自行分配编号。Pod ID 的格式是 `<个人目录名>-<index>`，例如 `huyuan-1`、`huyuan-2`。同一人的 Pod 共用 `/fsx/<个人目录名>`，每个 Pod 有独立的 SSH 端口和系统盘。旧式实例计作索引 1。
3. 选择代理时，指导用户复制 [Kato 配置模板](https://github.com/Urban-Visual-Intelligence-PKU/Lightweight-Proxy/blob/main/config/template.yaml)，将副本命名为 `<个人目录名>.yaml`，按注释填写 AnyTLS profile，通过私密渠道单独交给管理员。YAML 含凭据，避免提交到 Git 或发到群聊。

## 配置 SSH 并登录

1. 请用户提供管理员回复的一行登录命令，例如 `ssh -p 22226 root@192.168.10.2`。从中读取主机、端口和登录用户，在本机 `~/.ssh/config` 添加配置。别名可自定义。已知 Pod ID 时建议用它做别名，否则用个人目录名加 SSH 端口，例如 `huyuan-22226`。追加 Pod 时使用新的别名。

   ```sshconfig
   Host huyuan-22226
       HostName 192.168.10.2
       User root
       Port 22226
       StrictHostKeyChecking yes
   ```

2. 若本机已信任该地址和端口的主机密钥，直接运行 `ssh <别名>`。首次核验时，从可信渠道单独向管理员核对该端口对应的 Ed25519 主机密钥 SHA256 指纹，再运行 `ssh -o StrictHostKeyChecking=ask -o HostKeyAlgorithms=ssh-ed25519 <别名>`。只在提示的指纹一致时接受。若密钥不符或提示已知密钥变更，先停下来向管理员核实。登录使用与 GitHub 公钥配对的本机私钥。登录后运行 `pwd` 和 `ls -ld /fsx/<个人目录名>` 核对环境。

## 迁移数据

登录后收集源目录与可共享范围。已在使用 TrainingPod 的用户可直接从本节开始。同一用户追加 Pod 后，原来放在个人持久目录的内容可直接使用，旧 Pod 系统盘上的数据仍需按清单迁移。

新 Pod 在个人目录和 `/fsx/shared` 之间 `mv` 会直接改名，保留原属主、权限和 ACL。发布后核对接收方能读取。旧 Pod 双挂载和 `/root`、`/tmp` 与 `/fsx` 之间的移动仍会复制。大数据、checkpoint 和训练输出直接写入 `/fsx`。跨挂载 ACL 警告和复制替代命令见[用户指南中的存储规则](../../README.md#迁移数据)。

1. 确认使用者的目录名和源路径。源在宿主机 home 时，在宿主机执行 `cd -- "/home/<账号>"`（替换为实际账号），用只读操作逐项清点项目和数据，检查隐藏文件、符号链接、预计空间和仍在写入的任务。列出每个条目的源路径、是否迁移和目标路径。保留 home 目录本身及未选中的内容，禁止将整个 home 作为 `mv` 的源或用通配符批量移动其内容。对于混放代码和数据的目录，分别判断各子目录的去向。将选中的个人项目和私有数据归到 `/fsx/<个人目录名>`，将获准共享的原始下载数据归到 `/fsx/shared/data/raw/<数据集>`，保留原始内容。将获准共享的清洗、转换、切分或其他项目产物归到 `/fsx/shared/data/<项目名>/<数据集>/`，同时记录来源数据版本和处理方式。`raw` 是保留目录名。排除密钥、令牌、`.env` 和任何尚未确认可公开给预期使用者的内容。记录共享数据的来源、版本和使用许可。
   需要共享的个人文件和产物归到 `/fsx/shared/<个人目录名>`，共享数据集按上面的原始数据或项目路径归档。

   从 Hugging Face 以外的来源下载的公开 checkpoint 归到 `/fsx/shared/models/<模型名>/`。获准共享的 Hugging Face 和 ModelScope Hub 缓存归到 `/fsx/shared/models`，两者的 Datasets 缓存归到 `/fsx/shared/data`，保留 SDK 的目录和符号链接结构。Conda 共享包缓存由管理员从可信源填充。GPU 编译和自动调优缓存留在个人目录。
2. 在宿主机上处理 `/home/<账号>` 中的源。请管理员确认 `findmnt -M /fsx` 指向持久存储，并创建个人根目录或配置共享目标父目录的 ACL。确认实际搬运身份可以访问源和目标，目标目录名尚未使用，符号链接不会指向其他容器读不到或无权访问的位置。无法确认时，先完成能做的清点并报告具体缺项。
3. 按用户授权的清单逐个项目或数据目录执行 `mv`。先协调停止所选源路径的写入。在宿主机用 GNU `mv --no-clobber --no-target-directory -- "$src" "$dst"`，其中 `src` 和 `dst` 为已核对的绝对路径。迁移前用 `stat -c %d` 比较源与目标父目录的设备编号，检查目标路径及同名符号链接。迁移后检查源已经移走且目标存在，因为 GNU `mv --no-clobber` 跳过已有目标时可能仍返回成功。跨文件系统前先确认目标空间，并在移动前记录必要的文件校验和。GNU `mv` 此时会复制后移除源条目，操作并非原子。若中途报错，先检查源与目标的状态，再决定如何恢复。
4. 整目录移动会带着原有权限和 ACL。请管理员按共享范围检查并调整现有目录和文件的权限，同时为后续新文件配置默认 ACL。从用户的 Pod 读取代表性文件。若要共享给其他 Pod，再从一个获授权的 Pod 验证读取，约定可写时验证能创建并删除测试文件。
5. 更新任务配置中的数据路径并做一次小规模读取验证。向用户报告源与目标路径、是否已移动、权限和读取的实测结果，以及仍需管理员处理的事项。
